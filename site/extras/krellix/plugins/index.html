Build a Krellix plugin

Build KrellHello, a small monitor with a text readout and a moving bar. It uses the same C++ and Qt widgets as other Krellix monitors but needs no hardware, network service, or credentials.

Download KrellHello source Plugin SDK reference

1. Build and run KrellHello

A plugin is native code, not a theme. It runs in the Krellix process with your user permissions. Only load modules you trust. If you just want to change colors or artwork, build a theme instead.

Use the Krellix source checkout, a C++17 compiler, CMake 3.21 or newer, Ninja, and Qt 6 development libraries (Core, Gui, Widgets, Network, and DBus on Linux/macOS). Use the source and toolchain of the Krellix version you want to support. The opt-in example is under examples/krellhello; the ZIP contains those source files, not an installable binary.

Linux and macOS

Use your distribution's Qt 6 development packages on Linux. On macOS, install the Xcode command-line tools and matching Qt 6 development libraries. If CMake cannot find a Homebrew Qt installation, pass -DCMAKE_PREFIX_PATH="$(brew --prefix qtbase)" when configuring, if qtbase is the formula you installed.

cmake -S . -B build-author -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DKRELLIX_BUILD_EXAMPLES=ON -DBUILD_TESTING=OFF
cmake --build build-author --target krellix krellhello
cd build-author
KRELLIX_DEV_PLUGINS=1 ./bin/krellix --instance plugin-preview \
  --monitors host,krellhello

Windows x64

Use the matching MSYS2 UCRT64 compiler and Qt 6 runtime used for the portable host. In the UCRT64 shell, make the compiler, Qt tools, CMake, and Ninja available on PATH. Set KRELLIX_SENSOR_DIR to the sensors directory from the matching portable build (it contains krellix-sensors.exe), or build it using the sensor helper build script.

cmake -S . -B build-author -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DKRELLIX_BUILD_EXAMPLES=ON -DBUILD_TESTING=OFF \
  -DKRELLIX_SENSOR_DIR="C:/path/to/Krellix/sensors"
cmake --build build-author --target krellix krellhello
cd build-author
KRELLIX_DEV_PLUGINS=1 QT_FORCE_STDERR_LOGGING=1 \
  ./sensors-candidate/krellix.exe --instance plugin-preview \
  --monitors host,krellhello

Run those commands from the source root, then from build-author as shown. KRELLIX_DEV_PLUGINS=1 adds ./plugins relative to the working directory for that process only. KrellHello should show a changing counter and a bar. The named instance keeps test settings separate from your regular profile.

2. Give the factory and the monitor separate jobs

Plugin factory
Implement IKrellixPlugin in a QObject. Register Q_OBJECT, Q_PLUGIN_METADATA(IID KrellixPlugin_iid), and Q_INTERFACES(IKrellixPlugin). Use a unique reverse-domain ID and a version. Let CMake AUTOMOC generate the Qt metadata.
Monitor
Give each MonitorBase a stable slug id() and a displayName(). In createWidget(parent), use Panel, Decal, Chart, or Krell with the passed-in theme. The host owns the parented monitor and panel. Keep widget references in QPointer.
Updates
tick() runs on the GUI thread. Use it to apply results and schedule bounded background work, not to wait for a network request, a subprocess, or a slow filesystem. Request a sensible tickIntervalMs() and respect the host's global update cadence.
Teardown
Stop work in shutdown(). Cancel requests or processes, prevent overlapping polls, and ignore late results. Give Qt connections a QObject context. The host can recreate or discard a monitor during settings changes even if its plugin library remains loaded.

For bespoke settings, use an owned namespace under plugins/ in the current profile, with validated defaults. The current SDK does not automatically generate a plugin settings form. Use a namespaced test profile and avoid moving controls into the monitor if they belong in configuration.

Read the complete KrellHello implementation to see the factory, theme-aware panel, and tick method together.

3. Keep the client platform separate from the monitored host

Keep UI and formatting shared. Select local backends at build time with Qt's Q_OS_LINUX, Q_OS_MACOS, or Q_OS_WIN guards. At runtime, first ask whether the window represents a remote host. A Windows client can be showing Linux data; the Windows backend is not the right source for that window.

QList<MonitorBase *> createMonitors(Theme *theme,
                                     QObject *parent) override
{
    if (RemoteSource::instance())
        return {};
    return {new HelloMonitor(theme, parent)};
}

KrellHello uses this local-only pattern. For a remote-enabled plugin, use data from the active RemoteSource when available; do not silently substitute the client's counters. Show unavailable data and clear stale readings on disconnect. Not every metric is available from every daemon.

Use Qt's asynchronous APIs and known argument lists when calling a helper. Set deadlines and output limits, handle missing dependencies, validate external responses, and never log passwords, tokens, or private payloads. Test denied permissions and missing devices as normal states.

4. Test the module before installing it

  1. Use a fresh named instance and confirm that the factory loads and the panel actually updates. Pick IDs that do not collide with existing plugins or monitors.
  2. Change theme, width, ordering, and enabled monitors while it runs. Repeat opening/closing settings and quit while an operation is pending. Make sure a late reply cannot access a retired widget.
  3. Test a local, connected remote, and disconnected remote instance. Make sure a local-only monitor stays hidden remotely. For a network-backed monitor, use a controlled local fixture instead of real accounts.
  4. Test the final module with the actual packaged host and runtime for each advertised OS and architecture, not only an in-tree debug build.

If it does not show up

No loader message
Check the output folder, filename extension, and working directory. Development discovery requires KRELLIX_DEV_PLUGINS=1; regular user folders do not.
Load failure or missing symbol
Check the host build, Qt runtime, architecture, dependencies, and exported symbols. Use QT_DEBUG_PLUGINS=1 for detailed loader diagnostics; turn it off after debugging.
Factory ready, no panel
Check the monitor ID and whether the factory returns a monitor for that platform or remote mode. Check for duplicate monitor IDs. A loaded factory does not guarantee a panel was created.
Slow or crashes on close
Look for blocking calls in tick(), multiple in-flight requests, and callbacks that outlive the monitor. Reproduce in the test profile, then add a regression test.

5. Install, package, and share

For a user install, put the module itself directly in the right directory, not one folder deeper inside an archive. The host loads native modules at startup, so restart it after adding or replacing a binary.

Linux
~/.local/share/krellix/plugins/, or $XDG_DATA_HOME/krellix/plugins/ when set. Distribution packages normally use the host's system plugin path, such as /usr/lib/krellix/plugins/.
macOS
~/Library/Application Support/krellix/plugins/. Leave the signed Krellix.app bundle untouched.
Windows
%LOCALAPPDATA%\krellix\plugins\. The example links to the Windows host target; do not copy another build's Qt or C++ runtime DLLs over the installed ones.

One source archive can serve all platforms. Native binaries cannot: build separately for each advertised OS and architecture. Keep the plugin interface IID unchanged unless changing the interface itself, and document the actual minimum host and ABI compatibility. Matching io.krellix.IKrellixPlugin/1.0 alone does not guarantee binary compatibility.

Include a version, license, dependencies, install/remove steps, and a tested host matrix. For Pacman, DEB, and RPM, let the package manager own the module and declare the host version requirement. For archives, include a checksum and preferably a signature. Never overwrite an unknown or newer install. Share the sources and release notes in Krellix Discussions.
